# Sideloading

## Quick view

> Just add ?include=foo,bar to get additional information about linked items, and you will get additional node in response

```json
{
  "data": {
    "id": 2,
    "picture_blob": 3,
    "disable_picture": false,
    "is_agent": true,
    "is_deleted": false,
    "name": "Wilton Crooks",
    "organization": 24,
    "timezone": "Atlantic\/Canary",
    "date_created": "2015-10-03T09:33:58+0000",
    "primary_email": "prohaska.orville@example.net"
  },
  "meta": [],
  "linked": {
    "organization": {
      "24": {
        "id": 24,
         "name": "Walter-Steuber",
         "importance": 1,
         "employees_count": 19
      }
    }
  }
}
```

DeskPRO is full of entities. Each DeskPRO entity will be linked with another entity with chance 95%.

Usually links are processed as-is and at the output you will have full set of entities no matter how deep they are nested.

We know, that very, very often you aint gonna need that.
Only what you need to fetch an entity you want. For example it's just person if you are accessing /api/v2/people endpoint.

But sometimes you may want to fetch something linked with person.
For example it could be just organization. You have such ability - just add additional parameter to your get request and you will get what you want.

`GET http://localhost/api/v2/people?include=organization`

The additional node in **linked** will appear and each entity of this node would be the object,
where keys are ID of requested sideload entity.

Moreover there is no limitations about what to load. You can sideload **organization**, **language**, **usergroup**
with `/api/v2/people` endpoint and everything will be ok.

Also you should know, that sideloading is recursive.

It means just two things:

 * Your sideload could be chained: load (Ticket) -> sideload (Person) -> sideload (Usergroup).
 * Your sideload could be cycled, so person loads usergroup, that loads persons, that also load usergroup.

<aside class="warning">
Providing <code>?include=person,usergroups</code> can load almost all persons and usergroups if you are lucky enough.
<br/>
Therefore you should remember, that "With great power comes great responsibility" (c)
</aside>

## Limitations, rules  and errors

> Providing wrong type for include will give you an error

> Getting `http://localhost/api/v2/ticket_snippets?include=text_snippet_category,ticket_snippet_content` will result in

```json
{
  "status": 400,
  "code": "You can't sideload [ blah-blah ], available types for sideloading are [ blah-blah-blah ]",
  "message": "You can't sideload [ blah-blah ], available types for sideloading are [ blah-blah-blah ]",
  "errors": null
}
```

Unfortunately sometimes same types are masked under different nodes in our endpoints. For example: `owner`, `agent`, `creator`
- each of this nodes in API will point to `Person`, so to sideload `owner` you are still need to send `?include=person`, but not owner.

This is one of basic limitations and you have to accept it to work with sideloading.

But how to get appropriate string name for `include`? This is fair question you'll find in your head.
Good news is that you usually can gather this information from our [autogenerated docs](/api/v2/doc).

Take a note for **response** tab in some GET method. You will find something like **\\integer id (Organization)\\**.
Well that's it - **Organization** could be sideloaded. The main rule is to convert UpperCamelCase to snake_case.

Therefore **Organization** becomes **organization**, **TextSnippetCategory** becomes **text_snippet_category**,
so to sideload snippet categories you can just pass `?include=text_snippet_category` with your request.

Also you have to remember: if you will provide wrong type for include then you will get an error describing which types
was wrong and which types are available for this endpoint with given `?include` parameter.

That's said: available types for include depends on what you are included already.
